# Task 11 — Recommend and defend the final design

Use `enum class Zone`, a single fare table, integer paise in `long long`, validated input, and a `SmartCard` class with a private balance. This design keeps zone values explicit, prevents floating-point fare errors, and makes the minimum-balance rule a single controlled operation. Fare lookup and card authorization are O(1) per journey; processing n journeys is O(n). The tests in Task09 cover the peak boundaries, invalid inputs, exact Rs 50 remaining, and a hand-calculated five-trip total. Task10 demonstrates why `int` is too small for the network paise total and why repeated `double` addition is not exact. Task12 demonstrates how a table and a `MonthlyPass` can handle Airport, weekend fares, and covered zones.

A fare revision is made in the centralized table/policy, followed by boundary and regression tests. Adding Airport then requires a new enum value and fare entry; a table avoids copying a fare into multiple switch statements. A file-based fare table could be loaded once when the gate starts: reading z entries costs O(z) startup time and O(z) storage, after which lookups stay O(1). This avoids recompiling for every price change but requires validation, versioning, and safe behavior if the file is missing or malformed. A compiled `constexpr` table is simpler and safer for a small, stable policy.

Limitations: the assignment does not specify the student/senior concession percentage or rule ordering, so that must be confirmed before deployment. The examples assume 50% only as a replaceable value. A production system would also need persistent transaction records, authentication, concurrency control, audit logging, and explicit policy for refunds and pass expiry. The design remains suitable for millions of journeys because each journey uses constant-time fare and balance operations; total daily processing is linear in the number of journeys.
